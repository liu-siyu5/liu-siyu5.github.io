Two robots, one map

Where
Northeastern University
When
October – December 2024
Role
Course project
Stack
ROS, Gazebo, TurtleBot3, SLAM and the ROS navigation stack

Two TurtleBot3 robots exploring the same house, each building a map, both ending up in one. Getting a single robot to map and navigate is a well-trodden path. Adding a second one breaks things that had no reason to break, and that is most of what this project turned out to be.

One robot first

The coloured field is the costmap, not the map. The map is the black and white part — walls the laser has confirmed. Everything soft around it is inflation: the planner's own margin, grown outward from each obstacle so a robot with width is not planned through a gap it cannot fit. The dark curve is the global path, and the green dots are live scan returns landing on walls that were already there, which is what mapping looks like when localisation is holding.

Then the second robot breaks it

Two identical robots under one ROS master publish identical names. Both have a /scan. Both have an /odom. Both broadcast a transform from odom to base_link. Nothing in ROS stops them, so subscribers receive an interleaved stream from two machines and the transform tree ends up with one frame claiming two parents.

The symptom is not a crash. It is a robot that localises to somewhere it has never been.

The fix is to make every name carry the robot it belongs to — topics and transform frames alike — and to set that up in the launch files so it is structural rather than something each node has to remember. After that the two stacks stop overwriting each other and each robot has a coherent view of where it is.

Two maps into one

Separating them creates the opposite problem. Each robot now has its own occupancy grid covering the part of the house it has visited, and neither grid is the answer. I wrote a merge node that takes both and publishes a single live map, so the pair share what either one has seen.

Still to write up. The details of how the two grids are brought into a common frame belong here and I would rather go back to the code and get them right than reconstruct them from memory. Happy to walk through it in the meantime.
